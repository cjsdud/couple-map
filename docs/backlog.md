- 상태: ✅ **구현됨** (2026-08-02).

## 6. 알림 넓히기 + 알림 보관함 (2026-08-02 메모)

- 요구:
  - 지금은 '오늘'을 남길 때만 알림이 간다. **CUD가 생기면 이벤트별로 다른 문구**의 알림을.
    대상: 데이트 등록·수정·삭제, 도화지 꾸미기, 설정 등.

- 현재: `api/send-push.ts`가 kind='today' 하나만 처리(`MESSAGE_BODY` 맵), 하루 3건 상한(`push_log`).
  지난 알림을 다시 볼 방법은 없다 — 놓치면 끝.

### 설계 메모 — **미는 알림과 쌓이는 기록을 나눈다**

이 둘을 한 덩어리로 만들면 실패한다. 성격이 다르다.

| | 푸시(미는 알림) | 보관함(쌓이는 기록) |
|---|---|---|
| 비용 | 상대의 주의를 뺏는다 | 없음 (열어 볼 때만 본다) |
| 넣을 것 | 짝꿍이 **지금 알아야** 의미 있는 것 | 커플에게 일어난 일 **전부** |
| 상한 | 하루 3건 (명세 §5) | 없음 |

- 그래서 **모든 CUD는 보관함에 남기되, 푸시는 골라서** 보낸다.
  설정 바꿀 때마다 폰이 울리면 성가시고, 그건 명세 §5가 막는 종류의 알림이다.
- **삭제 알림은 특히 조심.** "짝꿍이 기록을 지웠어요"는 사실이라도 감정을 건드린다.
  보관함에는 남기고 푸시는 하지 않는 쪽을 권한다 — 사용자 확인 필요.
- 문구는 이벤트별로 다르되 **행위자 이름 + 무엇을**만. 평가·재촉 어휘 금지.
  예: "천영이 강릉 데이트를 남겼어요" / "천영이 도화지 색을 바꿨어요".

### 구현 스케치

- `0017_activity.sql`: `activity_log(id, couple_id, actor_id, kind, title, target_id, created_at)`
  + RLS(couple_id 격리). 읽음 표시는 `profiles.activity_read_at timestamptz` 한 칸이면 충분하다
  (개별 읽음 처리는 과하다 — 뱃지는 "마지막으로 본 뒤 새로 생긴 것" 개수).
- 남기는 지점: `useCreateRecord`/`useUpdateRecord`/`useDeleteRecord`/`useUpdateCouple`(테마·설정)/
  기념일 CRUD/`useSaveToday`. 훅마다 흩뿌리지 말고 **`logActivity(kind, title)` 한 함수**로 모은다.
- 푸시는 `api/send-push.ts`의 `MESSAGE_BODY`에 kind를 늘리고, 보낼 kind 화이트리스트를 서버에 둔다
  (클라이언트가 아무 kind나 보내 상대를 울리지 못하게 — 지금도 대상은 서버가 정한다).
- 화면: 절대 규칙 1(화면 3개)이라 **새 탭 금지**. 각 탭 헤더 오른쪽에 종 아이콘 + 안 읽은 수,
  누르면 바텀시트. 항목을 누르면 그 기록/화면으로.
- 상한: 보관함은 최근 100건만 보여주고 그 아래는 자르기 (무한 스크롤은 과하다).

- 상태: ✅ **구현됨** (2026-08-02). 열린 질문 3개는 설계 메모의 권고대로 정했다
  (사용자 지시 "물어보지 말고 진행" — 바꾸고 싶으면 말해 주세요):
  ①삭제는 푸시하지 않는다 (보관함만) ②설정 변경도 보관함에 남긴다 (푸시 없음)
  ③종 아이콘은 **세 탭 헤더 모두** — 어느 탭에 있든 한 번에 보인다.
  - `0017_activity.sql`: activity_log + RLS(couple 격리, append-only). **사용자가 아직 안 돌림** —
    안 돌려도 앱은 멀쩡하다 (테이블이 없으면 종이 조용히 숨는다). 읽음은 기기별 localStorage.
  - `logActivity()` 한 함수로 모음: 기록 등록/수정/삭제 · 기념일 추가/삭제 · 오늘 · 테마 · 설정.
    10분 안 같은 문구는 한 번만 (사진 연속 업로드 도배 방지).
  - 푸시 화이트리스트(api/send-push의 MESSAGES = today · record_create · anniversary_create)
    밖의 kind는 서버가 400 — 클라이언트가 뭐라 보내든 삭제·설정 푸시는 불가능.
  - 남은 것: 보관함 항목을 누르면 그 기록/화면으로 이동 (탭 전환 연결이 필요해 뒤로 뺐다).

    (localStorage 플래그). 우리 탭 맨 위에 초대 카드가 연결될 때까지 떠 있고,
    짝꿍이 들어오면 자동으로 사라진다 (pending 4초 폴링이 이미 있어 연결 즉시 반영).
  - 혼자 남긴 기록도 couple_id 기준이라 연결되면 짝꿍에게 그대로 보인다 — 카드에 그 안내 한 줄.

## 8. 관리자 페이지 /admin (2026-08-03 사용자 요청)

- 상태: ✅ **구현됨** (2026-08-03). 실사용자 유입 대비 운영 현황판.
  - 경로 `/admin` — /install과 같은 관문 층 (3탭 밖이라 절대 규칙 1 무관).
  - 데이터는 전부 `api/admin-stats`(service role)에서 — RLS는 열지 않는다 (절대 규칙 5).
    관리자 판별은 **ADMIN_USER_IDS 환경변수**. 미등록 계정이 열면 403과 함께 자기 id를
    보여줘서 그대로 복사해 넣으면 된다 (부트스트랩).
  - 맨 위 **성장·이용** 패널 (2026-08-03 추가): 이번 주 신규 가입(지난주 대비 증감) ·
    오늘 가입 · 이번 주/오늘 활동한 사람(가입자 대비 %) · 1인당 데이터 기록/오늘 참여 평균 ·
    실제로 써 본 사람 비율 + 최근 14일 신규 가입 막대. 숫자 하나만 두면 좋은지 나쁜지
    판단이 안 되므로 **비교 기준(지난주·전체 대비)을 항상 같이** 둔다.
  - 내용: 집계 타일(가입자·커플·기록·오늘·사진·푸시) + 최근 14일 일별 활동 차트 +
    사용자 목록(닉네임·이메일·커플 상태·마지막 활동, 펼치면 그 사람의 기록·오늘·활동 로그) +
    전체 최근 기록/오늘/로그 피드. `?mock=1`로 예시 미리보기.
  - **글 내용 포함** (운영자 결정 — 분석 목적): 기록 메모·스팟 한마디·오늘 일기·질문 답까지
    그대로 보인다. 사진 원본은 담지 않는다. ⚠️ 개인정보 처리방침(privacy.html)에
    운영자 열람 범위 명시 필요 — 사용자 액션.
